M04 — Defining Variables, Inputs and Outputs in Terraform

A self-guided tour: turn a hard-wired configuration into a parameterised one, and find out by experiment which value wins.

This tour walks you through parameterising a configuration, one part at a time. It shows you the moves — the blocks to write, the commands to run, the experiments to set up — and gives you checkpoints so you always know whether you're on track.

It does not do the thinking for you. Your brief asks you to work out several things yourself (they're called research prompts), and your write-up is where your answers go. Every time you see a Your turn box, that's one of those prompts. Do the investigating there; don't expect the answer from this page.

How to use this tour

Work through the six parts in order. Each part has the same simple shape:

BoxWhat it means
Try itA command or action to perform now.
CheckpointWhat you should see if you got it right. If you don't, stop and fix it before moving on.
Pause and predictThink before you act. Write down your guess, then check it against what actually happens.
ExampleA worked illustration of the shape of a file, a command's output, or a note's format. Placeholders sit in <angle brackets>; yours will differ.
Your turnOne of your brief's research prompts. Investigate it and record your answer in your write-up.
Watch outA common trap. Read it before you hit it.
Explain itA nudge to say something in your own words — this is what you'll be asked to teach later.

You'll see Example boxes often. They show you the shape of things — a file's structure, what a command's output looks like, how to lay out your notes — so the mechanics are never a surprise. Two rules about them:

  • An Example never contains the answer to a research prompt. If it looks like it might, it deliberately stops short: the last step is always yours.
  • Never paste an Example as your own evidence. Your evidence must be real output from your machine. Examples are teaching aids, not proof.

Keep two things at hand the whole way:

  • Your brief (brief.md) — the objective, the scope, the constraints, the deliverable and the definition of done. This tour follows the lab in that brief.
  • Your write-up (write-up.md) — your copy of write-up-template.md. Fill it in as you go, not at the end. When you fill in the "How to build it" section, write it for someone who will follow it with no trainer to ask.

Where does my code live? Not in this repository. Build in a folder of your own, and keep your code in your own GitLab repository. Link it from the header of your write-up. You may reuse your M03 network as the starting point.

Where you're headed

By the end of this tour you'll have:

  • a parameterised configuration in which the region, the network address ranges and the name prefix are all inputs;
  • a validation rule that rejects a bad address range at plan time;
  • a record of your precedence experiments, one source at a time, then combined;
  • a sensitive input and a sensitive output, with notes on what the marking does and does not hide;
  • two different sets of values that both plan cleanly, and everything destroyed;
  • evidence for every item in your brief's definition of done.

Before you start. Your brief's "Still open / ask your trainer" list here is short — the one item is how much detail your notes need. Confirm that with your trainer before you invest significant time.

Part 1Turning hard-wired values into inputs

Goal: replace the hard-coded region, address range and name prefix with variable blocks.

Try it

  1. Take your M03 network (or rebuild it) and find the hard-coded region, address ranges and name prefix.
  2. Replace each with a variable block that has a type and a description.
  3. Decide, for each input, whether to give it a default — or leave it required.
  4. Confirm the configuration is sound:
terraform fmt
terraform validate

Checkpoint

  • Every variable has type and description (DoD-02).
  • No region, address range or name prefix is left hard-coded in the main file (DoD-03).

Example — the shape of a variable block

variable "vpc_cidr" {
  type        = string
  description = "<what this input is for>"
  default     = "<a default value, or omit this line to make it required>"
}

The block's fields are shown here; which inputs deserve a default and which should be required — and the risk of each choice — is one of your research prompts.

Pause and predict

Before you plan, guess what Terraform will use for a variable that has a default and no value supplied. Then run it and check.

Your turn

  • Which inputs should have defaults and which should be required — and what is the risk of each?

Watch out. Don't leave a stray hard-coded region or CIDR behind. DoD-03 has a reviewer read the configuration and confirm the main file contains none of them.

Part 2Rejecting bad values at plan time

Goal: add a validation rule that stops a bad address range before anything is planned.

Try it

  1. Add a validation block to the address-range variable.
  2. Trip it on purpose:
terraform plan -var vpc_cidr=10.0.0.0/33
  1. Confirm the message you get is your error_message, and that nothing is planned for creation.

Checkpoint

  • The bad value is rejected at plan time.
  • The error carries your validation message, and the plan creates nothing (DoD-02).

Example — the shape of a validation block

variable "vpc_cidr" {
  type = string

  validation {
    condition     = <a condition that must be true for the value to be allowed>
    error_message = "<your message, shown when the condition is false>"
  }
}

The syntax is shown here. Which rules deserve plan-time validation, which are better left for AWS to reject at apply time, and where a typed variable stops being enough, are your research prompts — so the condition itself is left for you to work out.

Pause and predict

Before you run the command, predict: will the bad value be rejected, or will it reach AWS? Then run it.

Your turn

  • Which rules deserve plan-time validation, and which are better left for AWS to reject at apply time?
  • Where does a typed variable stop being enough?

Watch out. A validation rule you wrote but never triggered is not evidence. DoD-02 wants the real rejection output, so trip it and keep the result.

Part 3Deriving a value once with a local

Goal: name a value you use in more than one place, and use it everywhere from one definition.

Try it

  1. Find a value your configuration builds from other values and uses in more than one place.
  2. Define it once in a locals block.
  3. Replace the repeats with a reference to the local.
  4. Check:
terraform fmt
terraform validate

Checkpoint

  • At least one value is derived once and used in more than one place (DoD-03).

Example — the shape of a locals block

locals {
  name_prefix = "<a value derived from your inputs, used in more than one place>"
}

Your turn

  • When is a local value clearer than repeating an expression — and when does it hide too much?

Explain it. In one sentence, say why deriving a value once is easier to maintain than repeating it, as if to a teammate.

Part 4The precedence experiments

Goal: find out, by experiment, which source of a value wins — one source at a time, then combined.

This is the heart of the stage. Set it up carefully, because the results only mean something if each experiment isolates exactly one source.

Try it

  1. Supply one variable from one source at a time:
    • its default;
    • terraform.tfvars;
    • a *.auto.tfvars file;
    • -var;
    • -var-file;
    • a TF_VAR_ environment variable.
  2. Run terraform plan for each and record the value Terraform used.
  3. Keep each experiment mutually exclusive: exactly one source supplies the variable, so every result can be attributed to it.
  4. Only after every source has been tried alone, combine sources deliberately and see which wins.

Checkpoint

  • One plan per source, each showing the single source that supplied the value.
  • A combined run that shows the winner, with your record stating the order in which sources win — backed by your own evidence, not the docs (DoD-04).

Example — a .tfvars file

region      = "<region>"
vpc_cidr    = "<cidr>"
name_prefix = "<prefix>"

Example — recording the experiments (format)

#Source supplying the variableValue Terraform usedPlan evidence
1default<...><...>
2terraform.tfvars<...><...>
3*.auto.tfvars<...><...>
4-var<...><...>
5-var-file<...><...>
6TF_VAR_ environment variable<...><...>
7combined sources<...><...>

The table is the format; the values and your conclusion are yours.

Pause and predict

Before you combine sources, write down your guess at the order in which they win. Then run the combined experiment and compare.

Your turn

  • How does each way of supplying a value show up in a plan?
  • Why might a team still allow only one source per variable — and how would you enforce that?

Watch out. The brief makes this a hard constraint: keep the experiments mutually exclusive, and don't combine sources until every source has been tried alone. Mix them early and no result can be attributed.

Watch out. A .tfvars file is committed by default. Never put a real secret in one — that is exactly the leak this stage later guards against.

Part 5Sensitive inputs and outputs

Goal: mark a value sensitive and observe what the marking hides — using throwaway placeholders only.

Try it

  1. Add a variable marked sensitive = true, with a throwaway placeholder value.
  2. Make sure the value reaches Terraform without appearing in any committed file.
  3. Add an output marked sensitive.
  4. Watch what is displayed:
terraform plan
terraform output

Checkpoint

  • The plan does not display the sensitive input.
  • terraform output does not display the sensitive output.
  • No committed file contains the value.

Example — a sensitive variable and output

variable "placeholder_secret" {
  type      = string
  sensitive = true
}

output "placeholder_secret" {
  value     = var.placeholder_secret
  sensitive = true
}

Example — how a sensitive value is displayed (trimmed)

# in a plan
  + placeholder_secret = (sensitive value)

# from terraform output
placeholder_secret = <sensitive>

Observe what is shown — and notice that the value still exists. Where it can still be seen, and what the marking does and does not protect, is your research prompt.

Pause and predict

Before you plan, predict whether the sensitive value will appear in the plan output. Then run it and look.

Your turn

  • How should a sensitive value reach Terraform, and what are the risks of each way you tried?
  • Which outputs are worth exposing at all, and who is the audience for each?
  • What does marking a value sensitive hide — and where can it still be seen?

Watch out. Use throwaway placeholders for every sensitive input, and never a real credential. Then find out for yourself where a "hidden" value can still appear — don't take the marking for granted.

Part 6Two sets of values, then destroy

Goal: prove the configuration plans cleanly for two different sets of values, then clean up.

Try it

  1. Create two different .tfvars files — two different sets of values.
  2. Plan with each and confirm both plan cleanly:
terraform plan -var-file=<set-one>.tfvars
terraform plan -var-file=<set-two>.tfvars
  1. Look up what each resource bills, apply if you need to, then destroy everything:
terraform destroy

Checkpoint

  • Two clean, error-free plans, captured separately (DoD-01).
  • Everything destroyed, confirmed from the cloud side (DoD-06).

Pause and predict

Before you plan with the second set, guess whether anything will want to be replaced rather than created. Then look.

Your turn

  • Which values differ between environments, and where do they live?

Watch out. DoD-01 wants output for each set of values, not one run described as covering both. Paste each plan's result separately.

Part 7Wrap up

Goal: land the landing. Prove it's all done, clean up, then write it up.

7a. Self-check against your definition of done

Open your brief's Definition of done and walk it line by line. For each item, make sure your write-up's "Checkpoint evidence" section shows real pasted output (trimmed to the relevant lines, and redacted). In particular, make sure you have:

  • passing fmt/validate, and a clean plan for each set of values;
  • every variable with a type and description, and the bad-range rejection with your message and nothing planned;
  • confirmation the main file holds no hard-coded region, CIDR or prefix, and one local value used more than once;
  • one isolated experiment per source, then your combined run, and the order you concluded;
  • a sensitive input and a sensitive output, with what is displayed for each, and what the marking protects;
  • everything destroyed, confirmed from the cloud side.

7b. The clean-up gate

Before you call the stage done, confirm:

  • No stored credential, and no real secret in any file. Every sensitive example uses a placeholder.
  • No .tfvars with a real secret committed, and no state file committed — state stays local.
  • Nothing left running. Every resource is destroyed, confirmed from the cloud side.

Example — the ignore rule that keeps state out

.terraform/
terraform.tfstate*

The rule of thumb: keep state out, keep the lock file in. Confirm with git status that no terraform.tfstate appears, and that .terraform.lock.hcl stays committed.

  • What I'd do differently.

Brief

Stage: 4 of 9 · Builds on: M03 (you may reuse that work) · Feeds into: M05, M06, M07

Objective

By the end of this stage, you can turn a hard-wired configuration into a parameterised one, work out by experiment which source of a variable's value wins, and handle a sensitive input and a sensitive output so that secrets reach Terraform and leave it without being committed or casually displayed — using your own plans as the evidence, not the documentation's description. You use local values to derive a value once.

Scope

You experiment on your own configuration, not a worked example. Find out, and write down in your own words:

  • Input variables — what a variable declares, and the defaults you give it. Research: which inputs should have defaults and which should be required, and the risk of each.
  • Validation rules enforced at plan time — rules that reject a bad value before anything is planned. Research: which rules deserve plan-time validation and which are better left for AWS to reject at apply time, and where a typed variable stops being enough.
  • Supplying values — the ways to give a variable a value. Research: how each way of supplying a value shows up in a plan.
  • Variable value precedence — which source wins when several supply the same variable, found by hands-on experiment. Research: why a team might still allow only one source per variable, and how you would enforce that.
  • Keeping environment-specific values out of the main configuration — what belongs in the main configuration and what does not. Research: which values differ between environments and where they live.
  • Local values — naming and reusing derived values within a configuration. Research: when a local value is clearer than repeating an expression, and when it hides too much.
  • Sensitive input variables — marking them and getting their values into Terraform without committing them. Research: how a sensitive value should reach Terraform, and the risks of each way you tried.
  • Output values — what to expose and how to mark an output sensitive. Research: which outputs are worth exposing at all, and who the audience is for each.
  • What marking a value sensitive does and does not protect — what the marking does and does not protect, shown with placeholder values. Research: what marking a value sensitive hides, and where it can still be seen.

Stack constraints

  • Everything under Rules for every stage applies.
  • You use AWS only, with small, cheap resources.
  • Look up what each resource in your plan bills before you apply, and destroy everything at the end of the stage.
  • The AWS region, the network address ranges and the resource name prefix must all be inputs, and state is local in this stage and is never committed.
  • Validation uses only what Terraform provides natively, with no external policy tooling.
  • Your precedence experiments are mutually exclusive. Each lets exactly one source supply the variable, so every result can be attributed to that source.
  • Only after every source has been tried alone may you combine sources to establish which wins.
  • Use throwaway placeholder values for every sensitive input, and never use a real credential.
  • Per-environment backends and state (M05), sensitive values in state (M02), secrets managers and credential stores, policy-as-code engines and reusable modules (M07) are not part of this stage.

Deliverable

A parameterised AWS configuration in which region, network address ranges and the resource name prefix are inputs, with two different sets of values that both plan cleanly, plus a record of your precedence experiments and a configuration that handles a sensitive input and a sensitive output.

Lab

Goal. Turn a hard-wired configuration into a parameterised one, and find out by experiment which source of a value wins.

You do, in the sandbox.

  1. Take the network from M03 and replace the hard-coded region, address range and name prefix with variable blocks, each with a type, a description and a default.
  2. Add a validation block that rejects a bad address range, and test it with terraform plan -var vpc_cidr=10.0.0.0/33.
  3. Add a locals block for a name you use in more than one place.
  4. Run the precedence experiments: supply one variable from one source at a time — its default, terraform.tfvars, a *.auto.tfvars file, -var, -var-file and a TF_VAR_ environment variable — run terraform plan for each, then combine sources and see which one wins.
  5. Add a variable marked sensitive = true with a placeholder value and a sensitive output, and run terraform plan and terraform output to see what is hidden.
  6. Plan with two different .tfvars files, then destroy anything you applied.

You build and capture. The parameterised configuration is your deliverable. Capture an invalid range rejected at plan time, clean plans for both sets of values, one plan per experiment and one for the combined run, and what is displayed for the sensitive input and output.

Clean-up. Destroy everything you created.

Definition of done

  • DoD-01: Formatting and validation pass with no errors, and both sets of values produce clean, error-free plans (output for each), not one run reported as covering both.
  • DoD-02: Every variable has a type and a description, and an invalid network address range is rejected at plan time with your validation message and nothing planned for creation (output pasted), not a rule you wrote but never triggered.
  • DoD-03: The main configuration file contains no hard-coded region, network address range or name prefix, and at least one value is derived once as a local value and used in more than one place (a reviewer reads the configuration).
  • DoD-04: Your precedence record has one isolated experiment for each source — defaults, terraform.tfvars, *.auto.tfvars, -var, -var-file and environment variables — each showing the single source supplying the variable and the value Terraform used (plan output per experiment); after them you combined sources deliberately, and your record states the order in which sources win, backed by your combined-run evidence, not by the documentation.
  • DoD-05: At least one sensitive input is marked sensitive, its value reaches Terraform without appearing in any committed file, and the plan output does not display it; at least one output is marked sensitive, and your evidence shows what is displayed for it. Your notes state what marking a value sensitive does and does not protect, backed by what you observed with placeholder values only.
  • DoD-06: Everything you created is destroyed, confirmed from the cloud side, not only from Terraform's output.
  • DoD-07: Your write-up takes a first-time learner to a parameterised configuration that plans cleanly with two sets of values unaided — verified by you following it end to end from a clean state.
